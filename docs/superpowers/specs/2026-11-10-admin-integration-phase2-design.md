## D — ตารางเวลาเฉพาะวัน / เว้นวัน

**กฎอยู่ที่ระดับแผน ไม่ใช่ต่อเวลา** ทุกเวลาของแผนเดียวกันใช้กฎเดียวกัน มี 3 แบบ:

| แบบ | `days_of_week` | `interval_days` | ความหมาย |
|---|---|---|---|
| ทุกวัน | null | null | ทานทุกวัน (ค่าเดิม) |
| เฉพาะวัน | เช่น `{1,3,5}` | null | ทานเฉพาะวันที่เลือก; ISO: 1=จันทร์ ถึง 7=อาทิตย์ ตรงกับ `DateTime.weekday` ของ Dart |
| ทุก N วัน | null | N | ทานวันที่ `start_date` แล้วเว้นไป N วันต่อรอบ (N ≥ 2) |

ไม่ต้องเพิ่มตารางหรือคอลัมน์ ใช้คอลัมน์ที่มีใน `medication_schedules` แล้ว

### ฐานข้อมูล (เพิ่มใน `supabase/integration.sql` ของเว็บ รันซ้ำได้)

`save_plan` เพิ่มพารามิเตอร์ท้ายสุด `p_days_of_week int[] default null, p_interval_days int default null` เนื่องจากเปลี่ยนจำนวนพารามิเตอร์ ต้อง `drop function` ฉบับเดิมก่อนสร้างฉบับใหม่ มิฉะนั้นจะเกิดฟังก์ชันซ้อนกันสองฉบับ กฎการตรวจเพิ่ม:

- ตั้งทั้ง `p_days_of_week` และ `p_interval_days` พร้อมกันไม่ได้
- `p_days_of_week` ต้องไม่ว่าง ค่าอยู่ใน 1–7 และไม่ซ้ำ
- `p_interval_days` ต้องอยู่ใน 2–365 และต้องมี `p_start` (ไม่เช่นนั้นนับรอบไม่ได้)
- ข้อความข้อผิดพลาดเป็นภาษาไทยตามรูปแบบของฟังก์ชันเดิม

การปรับเวลา: เวลาที่ยังอยู่ **อัปเดตกฎในแถวเดิม** (ไม่ลบแล้วสร้างใหม่ เพื่อรักษาบันทึกการทานยาที่ผูกกับ `schedule_id`) เวลาใหม่ใส่กฎเดียวกัน เวลาที่ถูกเอาออกยังลบได้เฉพาะเมื่อไม่มีบันทึกการทานยา ตามกฎเดิม

### เว็บ

- ฟอร์มแผนยา: เพิ่มตัวเลือกกฎ (ทุกวัน / เฉพาะวัน / ทุก N วัน) เลือกวันได้หลายวัน หรือกรอก N
- ฟังก์ชันบริสุทธิ์ใน `src/lib/plans.ts`: `ruleLabel(daysOfWeek, intervalDays)` คืน "ทุกวัน", "จันทร์/พุธ/ศุกร์" หรือ "ทุก 2 วัน"; `validatePlanForm` เพิ่มข้อความตามกฎข้างบน; `planRowToView` แสดงกฎในตาราง
- ตัวแก้ไขแผนอ่านกฎเดิมของแผนมาใส่ฟอร์ม

### แอป

- `Med` เพิ่ม `List<int> days` (ว่าง = ไม่จำกัด) และ `int intervalDays` (0 = ไม่ใช้) ใน `toJson`/`fromJson` ข้อมูลเก่าในเครื่องที่ไม่มีฟิลด์นี้อ่านเป็น "ทุกวัน"
- `RemotePlan.fromJson` เลิกข้ามแถวเวลาที่มีกฎ ใช้กฎของแถวแรกตามลำดับเวลา (ฟังก์ชัน `save_plan` เขียนกฎเดียวกันทุกแถวเสมอ) ถ้าเป็น "ทุก N วัน" แต่แผนไม่มี `start_date` ให้ถือเป็น "ทุกวัน"
- ฟังก์ชันเดียว `isDueOn(Med med, String dateKey)` ใน `lib/logic/dose_items.dart` ตรวจ start/end, วันในสัปดาห์ และรอบ N วัน (นับจำนวนวันด้วย `DateTime.utc` เพื่อไม่ให้เวลาท้องถิ่นทำให้คลาดวัน) `itemsFor` และ `planNotifications` เรียกฟังก์ชันนี้ร่วมกัน เพื่อไม่ให้หน้าจอกับแจ้งเตือนขัดกัน
- แผนเก่าที่มีกฎอยู่แล้วในฐานข้อมูลจะเริ่มแสดงในแอปหลังอัปเดต ซึ่งเป็นพฤติกรรมที่ถูกต้อง

## E1 — Dashboard จริงบนเว็บ

หน้า `Dashboard.tsx` ปัจจุบันอ่านข้อมูลตัวอย่างที่ว่างเปล่า (`D.patients`, `D.logs`, `D.appts`) จึงไม่เคยแสดงอะไร เปลี่ยนให้อ่านจาก Supabase เอง (RLS กรองขอบเขตตามบทบาทอยู่แล้ว):

- **การ์ดตัวเลข:** ผู้ป่วยในความดูแล (นับ `patients`), ทานแล้ววันนี้, ทานเลทวันนี้, ข้ามวันนี้ (นับจาก `medication_logs` ที่ `scheduled_at` ตรงวันนี้ตามเวลาไทย)
- **กราฟ "สัดส่วนการทานยา":** ย้อนหลัง 7 วัน ต่อวัน = `taken ÷ (taken + skipped)` นับเฉพาะบันทึกที่ทานหรือข้าม ไม่นับ `pending` วันที่ไม่มีบันทึกแสดงเป็นว่าง ไม่ใช่ 0%
- **ผู้ป่วยที่ต้องติดตาม:** ผู้ป่วยที่มีบันทึก `skipped` หรือทานเลทในวันนี้ พร้อมปุ่มเปิดรายละเอียดผู้ป่วย
- **ตัดออก:** การ์ดนัดหมายและตัวเลขนัดหมาย เพราะนัดหมายยังไม่เชื่อมฐานข้อมูล (งาน A) แสดงข้อมูลตัวอย่างว่างเปล่าต่อไปไม่มีประโยชน์
- ตรรกะคำนวณแยกเป็นฟังก์ชันบริสุทธิ์ใน `src/lib/dashboard.ts`: `todayCounts(logs, now)`, `dailyRate(logs, now, days)`, `needsFollow(logs, now)` ใช้เวลาเขตไทย (UTC+7)
- สถานะโหลด/ข้อผิดพลาด/ว่าง ตามรูปแบบหน้าอื่น

## E2 — ข้อความจากผู้ดูแลถึงผู้ป่วย (Supabase Realtime)

### ฐานข้อมูล (เพิ่มใน `supabase/integration.sql`)

**`send_notification(p_patient_id uuid, p_title text, p_body text) returns uuid`** (security definer, `set search_path = public`, execute เฉพาะ `authenticated`):
1. ต้องเป็น `has_role('admin')` และ `is_active_user()` มิฉะนั้นโยน `42501` (ตาราง `notifications` ไม่มี policy insert จึงเขียนผ่านฟังก์ชันนี้เท่านั้น)
2. ผู้ป่วยต้องมีอยู่และ `user_id` ไม่เป็น null (ผูกแอปแล้ว) ไม่เช่นนั้นโยนข้อผิดพลาด "ผู้ป่วยรายนี้ยังไม่ได้เชื่อมแอป"
3. ตรวจ `p_title` 1–100 ตัวอักษร (หลังตัดช่องว่าง), `p_body` 1–500 ตัวอักษร
4. เพิ่มแถว `notifications(user_id = patients.user_id, type = 'admin_message', title, body, patient_id)` และ `audit_logs(action = 'send_notification')` คืน `id`

**Realtime:** เพิ่มตาราง `notifications` เข้า publication `supabase_realtime` (ตรวจก่อนว่ายังไม่อยู่ เพื่อให้รันซ้ำได้) RLS ที่มีอยู่ (`notif_r`: `user_id = auth.uid()` และบัญชีใช้งานอยู่) ใช้กับ Realtime ด้วย ผู้ป่วยจึงรับได้เฉพาะข้อความของตัวเอง

**ข้อสังเกต:** policy `notif_u` เดิมให้เจ้าของแก้แถวของตัวเองได้ทุกคอลัมน์ ไม่ใช่แค่ `read` ผลกระทบจำกัดที่ข้อความของตัวเอง เฟส Demo ไม่แก้ บันทึกไว้เป็นหนี้เทคนิค

### เว็บ

หน้ารายละเอียดผู้ป่วยเพิ่มปุ่ม "ส่งข้อความ" เปิดกล่องกรอกหัวข้อกับข้อความ จำกัดความยาวตามฟังก์ชัน แสดงข้อผิดพลาดจากฟังก์ชันตรง ๆ (เช่น ยังไม่ได้เชื่อมแอป) และปุ่มไม่แสดงเมื่อผู้ป่วยยังไม่ผูกแอป ฟังก์ชันตรวจ input ใน `src/lib/` ทดสอบด้วย Vitest

### แอป

- **`NoticeSync`** (ใหม่): เมื่อเข้าสถานะ `ready` ดึงข้อความที่ `read = false` เรียงเก่าไปใหม่ และสมัครรับ Realtime ของ `notifications` (insert, กรอง `user_id = auth.uid()`) ยกเลิกการสมัครเมื่อออกจากระบบ และดึงซ้ำเมื่อกลับมา foreground เพื่อกันกรณี Realtime หลุดช่วงที่ไม่ได้เชื่อมต่อ
- **แสดงผล:** ข้อความใหม่แต่ละรายการแสดงเป็นแจ้งเตือนในเครื่องผ่าน `NotificationService` เดิม จากนั้นตั้ง `read = true` บนเซิร์ฟเวอร์ รหัสข้อความที่แสดงแล้วเก็บใน `shared_preferences` (จำกัดล่าสุด 100 รายการ) กันแสดงซ้ำเมื่อ Realtime กับการดึงมาพร้อมกัน
- **กล่องข้อความ:** หน้าจอรายการอย่างง่าย "ข้อความจากผู้ดูแล" แสดง 30 ข้อความล่าสุด (หัวข้อ ข้อความ เวลา) เปิดจากเมนูตั้งค่าเดิม ไม่มีการตอบกลับ ใช้เมื่อผู้ใช้ปิดสิทธิ์แจ้งเตือนของระบบ ข้อความจึงยังอ่านได้
- **ออกจากระบบ:** ล้างรหัสที่แสดงแล้วและยกเลิก Realtime ตามกติกาล้างข้อมูลเดิม
- **ไม่มีเน็ต:** ข้ามรอบนั้นเงียบ ๆ ไม่แสดง error ตามแนวทางของ `MedSync`

## ข้อผิดพลาด

กฎตารางเวลาผิดรูปแบบ → ฐานข้อมูลปฏิเสธพร้อมข้อความไทย เว็บแสดงตามนั้น; แผนในฐานข้อมูลที่ข้อมูลกฎขัดกันเอง (เช่น ตั้งทั้งสองคอลัมน์จากการแก้นอกระบบ) → แอปใช้กฎของแถวแรก และ `interval_days` ที่ต่ำกว่า 2 ถือเป็นทุกวัน; ส่งข้อความหาผู้ป่วยที่ยังไม่ผูกแอป → ปฏิเสธพร้อมข้อความ; Realtime หลุด → ดึงซ้ำตอนกลับมา foreground; บัญชีผู้ป่วยถูกปิด → ไม่ได้รับข้อความ (RLS)

## การทดสอบ

- **DB (PGlite ชุดเดิม):** `save_plan` กฎทั้ง 3 แบบ, กฎผิด (ทั้งสองคอลัมน์, วัน 0/8/ซ้ำ/ว่าง, N=1/366, N ไม่มี start), เปลี่ยนกฎแล้วแถวและบันทึกเดิมยังอยู่; `send_notification` ผู้ป่วย/แพทย์/ญาติเรียกไม่ได้, admin ส่งได้, ผู้ป่วยที่ยังไม่ผูกแอปถูกปฏิเสธ, หัวข้อ/ข้อความว่างหรือยาวเกิน, ผู้ป่วย A อ่านข้อความของ B ไม่ได้, มี audit
- **เว็บ (Vitest):** `ruleLabel`, `validatePlanForm` กฎใหม่, `todayCounts`, `dailyRate` (วันที่ไม่มีบันทึก, ไม่นับ pending), `needsFollow`, ตรวจ input ข้อความ; `pnpm build` ผ่าน
- **แอป (flutter test):** `isDueOn` ทุกกฎรวมขอบวัน start/end, วันอาทิตย์ (7) และจันทร์ (1), รอบ N วันข้ามเดือน/ข้ามปี; `RemotePlan` อ่านกฎ; `Med` JSON round-trip และข้อมูลเก่าเป็นทุกวัน; `planNotifications`/`itemsFor` ใช้กฎร่วมกัน; `NoticeSync` (repository จำลอง): ข้อความใหม่ → แสดง 1 ครั้งและตั้ง read, ได้ซ้ำจาก Realtime กับการดึง → แสดงครั้งเดียว, ออกจากระบบล้างสถานะ; widget test หน้ากล่องข้อความ; `flutter analyze` ผ่าน
- **ตรวจมือ:** ตั้งแผนทานจันทร์/พุธ/ศุกร์ → แอปแสดงเฉพาะวันนั้นและแจ้งเตือนถูกวัน; ตั้งทุก 2 วัน; กดทานยาในแอป → Dashboard เว็บเห็นตัวเลขเปลี่ยน; ส่งข้อความจากเว็บขณะแอปเปิด → ขึ้นแจ้งเตือนทันที; ปิดแอป ส่งข้อความ แล้วเปิดแอป → ข้อความปรากฏ

## ข้อสมมุติและความเสี่ยง
