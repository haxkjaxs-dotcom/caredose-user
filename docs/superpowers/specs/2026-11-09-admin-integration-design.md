# CareDose — เชื่อมแอปผู้ป่วยกับเว็บผู้ดูแล (Supabase โปรเจกต์เดียวกัน)

วันที่: 2026-11-09 · ต่อยอดจาก `2026-11-05-login-profile-design.md` และ `2026-11-04-caredose-flutter-design.md`
งานครอบคลุม 3 ส่วน: ฐานข้อมูล Supabase `eokqjjodfgdpgzievgln` (ของเว็บเดิม), เว็บผู้ดูแล (repo `haxkjaxs-dotcom/caredose-admin`), แอป Flutter (repo นี้)

## เป้าหมาย

ผู้ดูแลภาพรวม (`admin`) กรอกเบอร์ผู้ป่วยและเพิ่ม/แก้ไขแผนยาบนเว็บ ผู้ป่วยล็อกอินแอปด้วยเบอร์ + OTP แล้วเห็นยาที่ผู้ดูแลสั่งและตั้งแจ้งเตือนจากยานั้น การกด "ทานแล้ว / ยังไม่ได้ทาน" ในแอปถูกส่งขึ้นเซิร์ฟเวอร์ให้ผู้ดูแลเห็นบนเว็บ ญาติ (`caregiver`) ดูข้อมูลผู้ป่วยบนเว็บได้อย่างเดียว

## การตัดสินใจที่ผู้ใช้อนุมัติแล้ว

- ใช้โปรเจกต์ Supabase ของเว็บ `eokqjjodfgdpgzievgln` เป็นฐานข้อมูลเดียว (โปรเจกต์ `tiascejzeskwdniimyny` เลิกใช้)
- ผู้ดูแลล็อกอินเว็บแบบเดิม: เบอร์โทรเป็นชื่อผู้ใช้ + PIN 6 หลัก (ไม่เปลี่ยนเป็น OTP จนกว่าจะมีผู้ให้บริการ SMS จริง)
- ญาติใช้เว็บ ไม่ใช่แอป (ผู้ดูแลสร้างบัญชีญาติบทบาท `caregiver` ผ่านหน้า "ผู้ใช้และสิทธิ์")
- ผู้ป่วยที่ผู้ดูแลยังไม่ได้เพิ่มเบอร์ในระบบ ล็อกอินแอปไม่ได้

## สิ่งที่เปลี่ยนจาก spec ก่อนหน้า

- ข้อมูลยากับบันทึกการทานยา ย้ายจาก "เก็บในเครื่องอย่างเดียว" เป็น "เซิร์ฟเวอร์เป็นหลัก มีสำเนาในเครื่อง"
- ตาราง `profiles` ที่แอปเคยใช้เก็บข้อมูลส่วนตัว เลิกใช้ ข้อมูลส่วนตัวย้ายไปที่ `patients` + `consents` (ตาราง `profiles` ของเว็บเป็นข้อมูลบัญชี ไม่แตะ)
- ข้อมูลตัวอย่างในแอป (ยา, แพทย์, ญาติ, นัดหมาย) เอาออก ผู้ป่วยจริงต้องไม่เห็นข้อมูลปลอม

## ขอบเขต

รวม: ฟังก์ชัน/ทริกเกอร์ใน DB, หน้า "แผนยา" และ "ประวัติการทานยา" บนเว็บ, การระบุสถานะผูกแอปในรายชื่อผู้ป่วย, แอป: เปลี่ยนไปโปรเจกต์ใหม่ + ผูกบัญชีด้วยเบอร์ + ดึงยา + ส่งบันทึกการทานยา

ไม่รวม (เฟสถัดไป): หน้านัดหมาย/ญาติ/แพทย์/ภาพรวมของเว็บ, นัดหมายและแพทย์ในแอป, ตารางเวลาแบบเฉพาะวัน (`days_of_week`) หรือเว้นวัน (`interval_days`), ระบบคำนวณสถานะ "พลาด" ฝั่งเซิร์ฟเวอร์, OTP จริงผ่านผู้ให้บริการ SMS, ระบบกันเดา PIN ของเว็บ, แก้ข้อมูลส่วนตัวหลังบันทึกครั้งแรก

## ฐานข้อมูล (ไฟล์ `supabase/integration.sql` ใน repo เว็บ รันซ้ำได้ ผู้ใช้รันเองใน SQL Editor)

**คอลัมน์ใหม่:** `patients.nickname text`, `patients.profile_completed_at timestamptz`

**`norm_phone(text) returns text`** (immutable): ตัดทุกตัวที่ไม่ใช่ตัวเลข; ถ้าขึ้นต้น `66` เปลี่ยนเป็น `0`; คืนผลที่ได้ (`0812345678` และ `66812345678` → `0812345678`)

**`claim_my_patient() returns uuid`** (security definer, `set search_path = public`, execute เฉพาะ `authenticated`):
1. ต้องมี `auth.uid()` และ `auth.users.phone` ที่ยืนยันแล้ว มิฉะนั้นโยน `42501`
2. ถ้ามี `patients.user_id = auth.uid()` อยู่แล้ว คืน `id` นั้นทันที (ไม่เปิดใช้บัญชีซ้ำ เพื่อไม่ล้มการปิดบัญชีโดย admin)
3. หา `patients` ที่ `user_id is null` และ `norm_phone(phone) = norm_phone(auth.users.phone)`: ไม่เจอ → คืน `null`; เจอมากกว่า 1 → โยน `P0001` "เบอร์ซ้ำในระบบ"; เจอ 1 → ตั้ง `user_id`, เพิ่ม `user_roles(uid,'patient')` (on conflict do nothing), ตั้ง `profiles.is_active = true` และ `profiles.phone`/`full_name`, เขียน `audit_logs` (`claim_patient`), คืน `patients.id`
4. ทริกเกอร์ `guard_admin_columns` ปรับให้ไม่บล็อกเมื่อเรียกจากในฟังก์ชัน (เงื่อนไขเดิมเพิ่ม `and current_user in ('authenticated','anon')`)

**`save_my_profile(p_nickname text, p_full_name text, p_age int, p_conditions text[], p_consent_version text) returns void`** (security definer): ต้องมีแถว `patients` ของตัวเอง (ไม่งั้นโยน `42501`); ตรวจ nickname 1–50, full_name 1–100, age 1–120, conditions ไม่ว่าง และ consent_version ไม่ว่าง; อัปเดต `patients` (`nickname`, `full_name`, `age`, `conditions = array_to_string(p_conditions, ', ')`, `profile_completed_at = now()`), อัปเดต `profiles.full_name`, เพิ่มแถว `consents(user_id, version, given_by = auth.uid())`, เขียน `audit_logs` พร้อมค่าเก่า/ใหม่

**`save_plan(p_plan_id uuid, p_patient_id uuid, p_medicine_id uuid, p_dose text, p_meal_relation text, p_start date, p_end date, p_note text, p_times text[], p_status text) returns uuid`** (security definer): `p_plan_id` เป็น null = สร้างแผนใหม่; ต้อง `can_manage_plan(p_patient_id)` และ `is_active_user()` ไม่งั้นโยน `42501`; ตรวจ dose ไม่ว่าง, `p_end >= p_start` (ถ้ามี), `p_status` เป็น `active`/`stopped`, `p_times` อย่างน้อย 1 ค่า รูป `HH:mm` ไม่ซ้ำ และยาต้อง `is_active`; ทำในธุรกรรมเดียว: อัปเดตหรือสร้างแผน แล้วปรับ `medication_schedules` โดยเก็บแถวของเวลาที่ยังอยู่ (ไม่ลบแล้วสร้างใหม่) เพิ่มเวลาใหม่ (`days_of_week`/`interval_days` เป็น null) และลบเวลาที่ถูกเอาออก **เฉพาะเมื่อเวลานั้นยังไม่มีบันทึกการทานยา** (การลบ schedule ลบ `medication_logs` ตามด้วย `on delete cascade`) ถ้ามีบันทึกแล้ว โยนข้อผิดพลาดบอกให้หยุดแผนนี้แล้วสร้างแผนใหม่แทน

**ทริกเกอร์ audit** บน `medication_plans` และ `medication_schedules` (insert/update/delete, security definer) บันทึก `audit_logs(actor = auth.uid(), action, table_name, row_id, old_value, new_value)` เพื่อให้ทุกบทบาทที่แก้แผนยามีร่องรอยโดยไม่ต้องเขียนจากเบราว์เซอร์ (กฎเดิมให้เฉพาะ admin เขียน audit จากเบราว์เซอร์)

**กฎสิทธิ์เดิมที่ใช้ต่อ (ไม่แก้):** ผู้ป่วยอ่านแผนยา/เวลาของตัวเองได้ (`plan_r`, `sched_r`), เพิ่มบันทึกการทานยาได้ถ้า `recorded_by = auth.uid()` (`log_i`), แก้บันทึกได้ภายใน 24 ชั่วโมงหลังเวลาที่กำหนด (`log_u`), ผู้ดูแล/แพทย์ที่ผูกกันและญาติที่มี `can_manage_plan` เท่านั้นที่แก้แผนยาได้ (`can_manage_plan`) ค่าเริ่มต้นของ `patient_caregivers.can_manage_plan` เป็น `false` จึงดูได้อย่างเดียว

**ต้องตรวจก่อนใช้กับข้อมูลจริง:** schema เขียนไว้ว่าฟังก์ชัน `has_role`, `can_see_patient`, `can_manage_plan` เป็นฉบับสร้างใหม่ ต้องรัน `supabase/tests/rls_check.sql` (เขียนในงานนี้ รันใน transaction แล้ว rollback) ยืนยันว่า: ผู้ป่วย A อ่านข้อมูลผู้ป่วย B ไม่ได้, ญาติแก้แผนยาไม่ได้, บัญชีที่ปิดอยู่ (`is_active = false`) อ่านอะไรไม่ได้, ผู้ป่วยแก้ `patients.user_id` ของตัวเองไม่ได้ และ `claim_my_patient()` ผูกได้เฉพาะแถวที่เบอร์ตรงและยังไม่มีเจ้าของ

## การแปลงข้อมูลยาระหว่างแอปกับเซิร์ฟเวอร์

ดึงด้วยคำสั่งเดียว: `medication_plans` ของผู้ป่วยที่ `status = 'active'` พร้อม `medicines(...)` และ `medication_schedules(...)`

| ฝั่งแอป (`Med`) | มาจากเซิร์ฟเวอร์ |
|---|---|
| `id` | `medication_plans.id` |
| `name` | `medicines.trade_name` ถ้าไม่ว่าง ไม่เช่นนั้น `generic_name` |
| `dosage` | `medication_plans.dose` |
| `meal` | `medication_plans.meal_relation` (ข้อความตามที่ผู้ดูแลกรอก) |
| `times` | `medication_schedules.time_of_day` แต่ละแถว ตัดเป็น `HH:mm` เรียงเวลา |
| `start` / `end` | `start_date` / `end_date` (`end_date` ว่าง → `''`) |
| `note` | `doctor_note` ถ้าไม่ว่าง ไม่เช่นนั้น `medicines.warning` |
| `color` | เลือกจาก `medColors` ด้วยแฮชของ `plan.id` (ไม่เก็บบนเซิร์ฟเวอร์) |

ตารางเวลาที่มี `days_of_week` หรือ `interval_days` ไม่เป็น null แอปเฟสนี้ไม่รองรับ: ข้ามแถวนั้น (ไม่ตั้งเวลา) และเว็บเฟสนี้สร้างเวลาแบบทุกวันเท่านั้น (ทั้งสองคอลัมน์เป็น null)

## เว็บผู้ดูแล (repo `caredose-admin` ทำบน branch ใหม่ ห้าม push/merge ถ้าผู้ใช้ไม่อนุญาต เพราะ push ไป `main` จะ deploy GitHub Pages อัตโนมัติ)

- **แผนยา** (ต่อหน้าที่ยังเป็นหน้าว่าง): เลือกผู้ป่วย → รายการแผนยา (ยา, ขนาด, ความสัมพันธ์กับมื้ออาหาร, ช่วงวัน, เวลา, สถานะ) เพิ่มแผน (เลือกจาก `medicines` ที่ใช้งานอยู่ + ขนาด + มื้ออาหาร + วันเริ่ม/สิ้นสุด + หมายเหตุ + เวลาทานได้หลายค่า `HH:mm`) แก้ไข หยุดแผน (`status = 'stopped'`) การเพิ่มแผนและเวลาทำเป็นธุรกรรมเดียว (ผ่านฟังก์ชัน DB `save_plan(...)` security definer ที่ตรวจ `can_manage_plan` เอง) ปุ่มแก้ไขแสดงเฉพาะผู้ที่แก้ได้ แต่ความปลอดภัยพึ่ง RLS ไม่ใช่การซ่อนปุ่ม
- **ประวัติการทานยา** (ต่อหน้าที่ยังเป็นหน้าว่าง): อ่าน `medication_logs` พร้อมผู้ป่วย/ยา กรองตามผู้ป่วย วัน และสถานะ แสดงสถานะ ทานแล้ว / เลท (`taken` + `is_late`) / ยังไม่ได้ทาน (`skipped`) จำกัดครั้งละ 200 แถว ระบบเฟสนี้ไม่คำนวณ "ยังไม่บันทึก/พลาด"
- **รายชื่อผู้ป่วย:** เพิ่มคอลัมน์ "เชื่อมแอปแล้ว" (`user_id` ไม่เป็น null); ช่องเบอร์ในฟอร์มเพิ่มผู้ป่วยบังคับเป็นเบอร์มือถือไทย 10 หลัก (06/08/09); คอลัมน์ `phone` ที่ซ้ำกันในผู้ป่วยหลายคนต้องถูกเตือน (เพราะผูกบัญชีไม่ได้)
- ไม่เพิ่มคีย์ลับในเว็บ ใช้ publishable key เท่านั้น

## แอป Flutter

**Config:** `lib/config.dart` ชี้ `https://eokqjjodfgdpgzievgln.supabase.co` และ publishable key ของโปรเจกต์นั้น (ค่าสาธารณะที่อยู่ใน `pages.yml` ของเว็บ)

**ล็อกอิน:** หลัง `verifyOtp` สำเร็จ เรียก `rpc('claim_my_patient')`
- คืน `null` → สถานะใหม่ `AuthStatus.notRegistered` หน้าจอ "ยังไม่พบเบอร์นี้ในระบบ กรุณาติดต่อผู้ดูแล" พร้อมปุ่ม "ลองใหม่" (เรียก claim อีกครั้ง) และ "ออกจากระบบ"
- คืน id → ตรวจ `patients.profile_completed_at`: ไม่ null → `ready` (โหลดโปรไฟล์จาก `patients`: `nickname`, `full_name`, `age`, `conditions`, `consentAt = profile_completed_at`); null → `needsProfile`
- `init()` กรณีมี session: เรียก `claim_my_patient()` ก่อนทุกครั้งที่ไม่พบแถวผู้ป่วย (ผู้ดูแลอาจเพิ่มเบอร์หลังจากนั้น)
- `saveProfile` เรียก `rpc('save_my_profile', ...)` ด้วยค่าเดิมของฟอร์ม (ชื่อเล่น, ชื่อจริง, อายุ, โรค) และ `p_consent_version = '2026-11'`
- `AuthRepository` ปรับ: `Future<String?> claimPatient()`, `loadProfile()` อ่านจาก `patients`, `saveProfile()` เรียกฟังก์ชัน; ข้อผิดพลาดยังแปลงเป็น `AuthFailure`

**ซิงก์ยา:** `MedSync` (ใหม่) ดึงแผนยาตามตารางแปลงด้านบนเมื่อ (ก) เข้าสู่สถานะ `ready`, (ข) แอปกลับมา foreground, (ค) ทุก 5 นาทีขณะเปิดแอป ผลแทนที่ `AppData.meds` ทั้งชุด และสั่งตั้งแจ้งเตือนใหม่เมื่อรายการเปลี่ยน ถ้าดึงไม่ได้ (ไม่มีเน็ต) ใช้ยาที่เก็บในเครื่องล่าสุด ไม่ล้างข้อมูล

**ส่งบันทึกการทานยา:** `LogSync` (ใหม่)
- เมื่อกด ทานแล้ว / ยังไม่ได้ทาน / ทานทั้งมื้อ ส่ง `upsert` ไปที่ `medication_logs` (`onConflict: 'schedule_id,scheduled_at'`) ด้วย `plan_id`, `schedule_id` (จากเวลาตรงกับ schedule ของแผน), `scheduled_at` (เวลาท้องถิ่น → UTC), `status` (`taken` | `skipped`), `taken_at = now`, `is_late = (taken_at − scheduled_at) > 60 นาที` (เฉพาะ `taken`), `recorded_by = auth.uid()`
- ยกเลิกการบันทึก → `update` ตั้ง `status = 'pending'`, `taken_at = null` (ได้ภายใน 24 ชั่วโมงตามกฎสิทธิ์; ถ้าถูกปฏิเสธให้แสดงข้อความและคงสถานะเดิม)
- คิวส่ง (outbox) เก็บใน `shared_preferences` คีย์ `caredose_outbox`; ส่งซ้ำเมื่อเปิดแอป, กลับมา foreground และหลังซิงก์ยาสำเร็จ; ลำดับการดำเนินการต่อรายการเดียวกันคงเดิม; รายการที่เซิร์ฟเวอร์ปฏิเสธถาวร (สิทธิ์) ถูกทิ้งและบันทึก log
- ดึงบันทึกย้อนหลัง 30 วันจากเซิร์ฟเวอร์รวมกับของเครื่อง (สถานะ `taken`/`skipped` จากเซิร์ฟเวอร์ชนะ) เพื่อให้ประวัติอยู่ครบหลังติดตั้งใหม่
- ปุ่มบนการแจ้งเตือนที่บันทึกการทานยา (ทานแล้ว, ยังไม่ได้ทาน) ผ่านคิว `caredose_pending` เดิม แล้ว `AppState` ใส่เข้าคิวส่งตอนนำไปใช้ ส่วนปุ่ม "ยังไม่ทาน" บนการแจ้งเตือน (ปิดเตือน ไม่บันทึก) ไม่ส่งอะไรขึ้นเซิร์ฟเวอร์

**ข้อมูลตัวอย่าง:** `AppData.seed` เหลือเฉพาะค่าเริ่มต้นของการตั้งค่า (ไม่มียา แพทย์ ญาติ นัดหมาย); หน้าจอใช้ข้อความ "ยังไม่มีรายการ" เดิม; หลังไม่มียา หน้าหลักขึ้น "ยังไม่มียาในวันนี้ แพทย์จะเป็นผู้เพิ่มยาให้"

**ออกจากระบบ:** พยายามส่งคิวที่ค้างก่อน (รอไม่เกิน 5 วินาที) แล้วล้างข้อมูลในเครื่องตามเดิม รวมคิวส่งที่ยังส่งไม่ได้ (ผู้ใช้ถูกเตือนในกล่องยืนยันว่าบันทึกที่ยังไม่ได้ส่งจะหาย)

## ข้อผิดพลาด

เบอร์ไม่พบ → หน้า `notRegistered`; เบอร์ซ้ำ → "เบอร์นี้ซ้ำในระบบ กรุณาติดต่อผู้ดูแล"; ไม่มีเน็ตตอนซิงก์ → ใช้ข้อมูลในเครื่อง ไม่แสดง error บล็อกการใช้งาน; ผู้ดูแลหยุดแผนยา → รายการหายจากแอปภายในรอบซิงก์ถัดไปและแจ้งเตือนที่ตั้งไว้ถูกยกเลิก; บัญชีถูกปิดโดย admin → ข้อมูลที่ดึงไม่ได้ แอปใช้ข้อมูลในเครื่อง และผู้ป่วยเห็นข้อความจากหน้าจอปกติ (เซิร์ฟเวอร์ตอบว่าง ไม่ใช่ error)

## การทดสอบ

- **DB:** `supabase/tests/rls_check.sql` ตามรายการข้างบน (ผู้ใช้รัน) + ตรวจ `norm_phone` ด้วยตัวอย่าง `0812345678`, `66812345678`, `+66 81-234-5678` และ `claim_my_patient`/`save_my_profile` ทุกกรณีผิดพลาด
- **เว็บ:** ฟังก์ชันแปลงข้อมูล (สถานะ log → ข้อความ, ฟอร์มเวลา, ตรวจเบอร์) ด้วย Vitest; type-check และ `pnpm build` ผ่าน
- **แอป:** unit test ตัวแปลง `Med`, การสร้างคำสั่ง upsert/undo, คิวส่งและการส่งซ้ำ (repository จำลอง), `AuthState` สถานะใหม่ (`notRegistered`, `claim` ซ้ำ, ไม่ซ้ำทุกครั้ง), `AppState` เมื่อยาเปลี่ยนต้อง reschedule, ออกจากระบบล้างคิว; widget test หน้า `notRegistered`
- **ตรวจมือบน emulator + เว็บ:** admin เพิ่มผู้ป่วยเบอร์ `0812345678` + แผนยา → แอปล็อกอินด้วยเบอร์ทดสอบเห็นยา → กดทานแล้ว → เว็บเห็นในประวัติ → admin หยุดแผน → แอปไม่แสดงยานั้น

## ข้อสมมุติฐานและความเสี่ยง

- ผู้ใช้ต้องเปิด Phone provider + เบอร์ทดสอบ (`66812345678=123456`, วันหมดอายุไกลพอ) ในโปรเจกต์ `eokqjjodfgdpgzievgln` และมีบัญชี admin ของเว็บอยู่แล้ว (ตามขั้นตอนท้ายไฟล์ `schema.sql`)
- เครื่องมือ Supabase ของผู้ช่วยมองไม่เห็นโปรเจกต์นี้ ผลฝั่ง DB ยืนยันได้จากการรันสคริปต์ทดสอบและลองจริงเท่านั้น
- เปิดสมัครสมาชิกใหม่ของ Supabase เพื่อให้ผู้ป่วยสมัครด้วย OTP จะทำให้ใครก็สมัครบัญชีได้ แต่บัญชีใหม่ `is_active = false` มองไม่เห็นข้อมูลใด ๆ จนกว่า `claim_my_patient()` ผูกสำเร็จ
- เบอร์ที่ถูกโอนต่อให้คนอื่น: คนใหม่ยืนยัน OTP แล้วผูกกับผู้ป่วยเดิมได้ถ้าผู้ดูแลยังไม่ได้ผูกแถวนั้นไว้ (เฟสนี้ผู้ดูแลต้องตรวจเบอร์ให้ถูกคนก่อนให้ผู้ป่วยติดตั้ง และเว็บแสดงสถานะ "เชื่อมแอปแล้ว")
- ข้อมูลสุขภาพ (โรคประจำตัว ยา ประวัติ) อยู่บนคลาวด์ ภูมิภาคตามโปรเจกต์ที่มีอยู่ ต้องตรวจเรื่อง PDPA ก่อนใช้งานจริง
- ระบบกันเดา PIN ของเว็บยังไม่มี ห้ามใช้กับข้อมูลผู้ป่วยจริงจนกว่าจะทำ
- `is_late` 60 นาทีเป็นค่าที่ผู้ช่วยตั้งเอง เปลี่ยนได้ในแผนงาน
